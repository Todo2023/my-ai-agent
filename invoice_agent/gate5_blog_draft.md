# 請求書エージェントを作って分かった「大きいモデルほど良い」の嘘

## はじめに

プログラミング未経験の状態から、「請求書を自然文の指示で自動作成するAIエージェント」を作った記録です。動くものを作ること自体より、**どこで壊れたか・なぜ壊れたか**を記録することに重点を置きました。同じような学習の進め方をしている人の参考になればと思います。

## 作ったもの

Excelの顧客データ（顧客名・品目・数量・単価）をもとに、「A社の請求書を作って」のような自然文の指示から請求書PDFを作るエージェントです。構成はシンプルで、

- Python + LangGraph
- LLM: Google Gemini API（Gemma系の軽量モデル、無料枠）
- 決定的な処理: Excel読み込み・金額計算・PDF生成

## 最初のバージョンで起きたこと

最初は「LLMに直接ツールを呼ばせる」という素朴な作り方をしました。動くには動きましたが、わざと変な指示を30個投げてみたところ、看過できない問題が見つかりました。

- **対応していない機能について「対応した」と嘘の報告をする**（消費税計算に対応していないのに「消費税込みで作成しました」と報告してくる）
- **ツールが対応していない要求を無視したまま、確認なしで処理を確定させる**（割引の指定を無視して普通の請求書をそのまま作ってしまう）
- **LLMが存在しないツール名を呼び出し、プログラムがクラッシュする**

いずれも、実際の請求書業務で起きたら金額のミスや信用問題に直結する類のものです。

## 直し方: LLMの仕事を「情報を抜き出すだけ」に絞る

対策は、LLMに任せる範囲を大きく減らすことでした。

- LLMの仕事は「自然文から顧客名や特殊要求を抜き出す」ことだけに限定
- 何を実行するか・実行してよいかの判断は、普通のコードの条件分岐に戻す
- ユーザーに見せる最終的な文章も、LLMに語らせず、コード側で組み立てる
- ツールが対応していない要求が見つかったら、実行前に必ず人に確認を取る

LangGraphでワークフローとして組み直し、"LLMが判断する部分" と "決定的な処理" を明確に分けました。この変更だけで、ゲート2で見つけた重大な問題はすべて再現しなくなりました。

## 「測ってみたら大きいモデルの方が悪かった」という発見

評価用に22件のテストケース（入力と期待する挙動のペア）を作り、2つのモデルで比較しました。「新しい／大きいモデルの方が賢いはず」という前提で、あえて大きめのモデルも試したところ、

| モデル | 成功率 | レイテンシ |
| --- | --- | --- |
| 小さいモデル | 90.9% | 1.14秒 |
| 大きいモデル | 68.2% | 1.48秒（+30%） |

**大きいモデルの方が、遅くて、しかも不正確**という結果になりました。原因は、指定したJSON形式を守れずに出力が壊れ、6/22件でクラッシュしていたことです。「大きい・新しいモデルを使えばとりあえず安心」という思い込みは、少なくともこのタスクでは通用しませんでした。

## まだ残っている課題

正直に書きます。

- 「全ての顧客データを消して」という指示が、「全顧客の請求書を作って」と誤認されるケースがある（削除依頼と一括作成依頼を混同する）
- 複数の顧客を同時に名指しする指示（「A社とB社の請求書を作って」）にはまだ対応できていない
- 円換算のコストは、開発環境の制約で正式な単価を裏取りできておらず、トークン数までしか言えない

## まとめ

- エージェントは「作れるかどうか」より「どこで壊れるか」を先に知ることの方が大事
- LLMに全部任せると、精度もコストも安全性も悪化する。判断が必要な部分だけLLMに残し、残りは普通のコードに戻す設計が効く
- 「大きいモデル＝良い」は思い込みで、実際に測るまで分からない
