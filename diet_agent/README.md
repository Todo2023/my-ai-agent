# ふたりのダイエット記録（写真OCR）

夫婦2人で使う体重記録アプリです。**体重計の写真を撮ると、数字が自動で入力欄に入ります。**
スマホのブラウザから開いて使います。

```
[夫] [妻]              ← 撮る前に自分を選ぶ

📷 体重計を撮る         ← タップするとカメラが起動
   ↓（Geminiが写真の数字を読む）
日付   2026-08-16
体重   62.4 kg          ← 自動で入る（青枠＝OCRが入れた値）
体脂肪 18.2 %
       [この内容で保存]  ← 人間が確認してから保存
```

保存すると、ふたりの推移グラフ・先週比・目標までの残りが更新されます。

## まず動かしてみる（APIキー不要）

```bash
cd diet_agent
pip install -r requirements.txt
python demo.py                  # ターミナルで読み取り〜保存の流れを確認
DIET_FAKE_OCR=1 python app.py   # ダミーOCRでWeb UIを触る（http://localhost:8000）
```

`DIET_FAKE_OCR=1` のときは Gemini を呼ばず、固定のダミー値を返します。UIの確認用です。

## 本番で使う

```bash
export GEMINI_API_KEY=xxxxx     # https://aistudio.google.com/apikey で無料取得
export DIET_USERS=たろう,はなこ  # 省略時は「夫」「妻」
python app.py
```

起動後、同じWi-Fiにいるスマホから `http://<PCのIPアドレス>:8000` を開けば、
その場で写真を撮って記録できます。データは `diet.db`（SQLite）に入ります。

| 環境変数 | 既定値 | 説明 |
| --- | --- | --- |
| `GEMINI_API_KEY` | （必須） | Gemini APIキー |
| `GEMINI_MODEL` | `gemini-3.6-flash` | 画像を読むモデル |
| `DIET_USERS` | `夫,妻` | 記録する2人の名前 |
| `DIET_DB_PATH` | `diet.db` | SQLiteファイルの場所 |
| `DIET_PORT` | `8000` | 待ち受けポート |
| `DIET_FAKE_OCR` | （未設定） | `1` でダミーOCR |

> インターネットに公開する作りにはしていません（認証がありません）。家庭内LANで使ってください。

## 設計の考え方

### 読み取りはLLM、採否は決定的な処理

体重計の7セグメント表示は、既存のOCRライブラリが最も苦手とするものです（`8` と `0`、
`6` と `5` の取り違え、小数点の消失）。ここはLLMのvisionに任せます。

一方で、LLMは平気で桁を間違えます。そこで **`ocr.read_scale_photo()` が返す値は必ず
`ocr.validate()` を通し、決定的なルールで採否を決めます**（`ocr.py`）。

| ルール | 挙動 |
| --- | --- |
| 20〜250kg の範囲外 | 値を捨てて「手入力してください」 |
| `624` のように小数点が落ちた形 | `62.4` に補正し、**補正したことを警告として残す** |
| 体脂肪率が 3〜60% の範囲外 | 体脂肪率だけ捨てる（体重は残す） |
| 前回から3kg以上の変化 | **値は捨てず**、読み間違いの可能性として確認を促す |
| モデルの自信が0.6未満 | 確認を促す |

値を書き換えるときは必ず警告を残す、という原則にしています。黙って直すと、
間違った補正に気づけなくなるためです。

### 保存の前に必ず人間を挟む

`POST /api/ocr` は**読むだけで保存しません**。返ってくるのは候補値で、
UIのフォームに入るだけです。保存は人間が確認して `POST /api/records` を呼んだときだけ。

体重は毎日積み上がるデータなので、1件の誤記録がグラフと平均を汚し続けます。
撮り直しはタダなので、確認を挟むコストの方が安いという判断です。

### 日々の増減ではなく週平均で比べる

体重は食事・水分・時間帯で1kg程度は簡単に動きます。前日比で一喜一憂しても意味がないので、
サマリの「先週比」は **直近7日平均と、その前の7日平均の差** にしています（`store.summary()`）。

### 同じ日は上書き

朝と夜で撮り直すことがあるため、`(ユーザー, 日付)` を主キーにして上書きします。
「二重に記録してしまった」という一番ありがちな事故が起きません。

## ファイル構成

| ファイル | 役割 |
| --- | --- |
| `ocr.py` | 写真 → 数字。Gemini呼び出しと、決定的な検証（`validate`） |
| `store.py` | SQLiteへの保存、集計（週平均・目標までの残り） |
| `app.py` | FastAPIのWebサーバ。`/api/ocr` は読むだけ、`/api/records` で確定 |
| `static/index.html` | スマホ向けUI（カメラ起動・グラフ・一覧）。依存ライブラリ無し |
| `demo.py` | APIキー無しで流れを確認するデモ |
| `test_diet_agent.py` | 検証ロジック・保存・APIのテスト（Geminiは呼ばない） |

## テスト

```bash
pytest -q
```

Geminiは呼ばないので、APIキー無しで通ります。読み取りの正しさそのものではなく、
**「LLMが変な値を返したときにアプリが正しく踏みとどまるか」** を検証しています。
