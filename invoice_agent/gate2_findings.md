# ゲート2: 壊す（失敗ケース分析）

対象: `invoice_agent`（請求書エージェント）
モデル: `gemma-4-26b-a4b-it`（Gemini API 経由、無料枠）
テスト方法: `gate2_run.py` で30個の指示を自動実行し、結果を `gate2_results.json` に記録

## 分類の凡例

| 記号 | 意味 |
| --- | --- |
| OK | 期待通り、または安全に対応できた |
| 要注意 | クラッシュはしないが、誤った/不正確な結果や挙動のブレがある |
| NG | クラッシュ、または実害につながりうる誤動作 |

原因分類:
- **データ** = 入力データの問題（そもそも情報が無い／表記ゆれに対応するデータが無い）
- **モデル** = モデルの能力の問題（意味の取り違え、ハルシネーション）
- **ツール設計** = ツール設計の問題（機能不足、未定義呼び出しへの対応不足、LLMの選択ミス）
- **プロンプト** = プロンプトの問題（役割・方針が指示されておらず挙動が安定しない）

## 原因分類の集計

| 分類 | 件数 | 該当 |
| --- | --- | --- |
| ツール設計の問題 | 4件 | #7, #9, #15, #21 |
| モデルの能力の問題 | 3件 | #10, #12, #18, #24（#18/#24はハルシネーション） |
| プロンプトの問題 | 1件 | #19 |
| データの問題 | 0件 | - |

**最も多いのは「ツール設計の問題」。** 次いで「モデルの能力の問題」、特にハルシネーション（#18, #24）は実務上もっとも危険。ツールが対応していない要求に対して「対応した」と嘘の報告をするのは、請求金額のような実害に直結するミスにつながる。

## 最重要の発見（優先度順）

1. **#18 / #24: ハルシネーション（虚偽の完了報告）** — 対応していない機能について「実行した」と報告する。金額や内容に関わる請求書エージェントでは致命的。
2. **#15: 確認なしの黙示的な実行** — 要求の一部（割引）を無視したまま、残りの処理を確認なく確定させた。不可逆操作（PDF確定）の前に承認を挟む設計が必要。
3. **#21: 未定義ツール呼び出しでのクラッシュ** — LLMが存在しないツール名を生成した場合の防御が無い。
4. **#9: 顧客一覧を取得する手段が無い** — ツールの機能不足。

これらはいずれも「ゲート3: 構造化する」で対処する（決定的なガード処理の追加、実行前の確認ステップ、ツールの拡充）。
