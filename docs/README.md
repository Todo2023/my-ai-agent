# 設計メモ

コミュニティを2つ作るための検討メモ。ここにコードはない（作ったものは `../biz/` と `../ehon/`）。

| | | |
| --- | --- | --- |
| [`platform-marketing.md`](platform-marketing.md) | **マーケ・ビジネス版** | Zennのマーケティング／ビジネス版。書き手は社会人 |
| [`platform-kids.md`](platform-kids.md) | **子ども向けの本・絵本版** | 絵本・児童書を投稿して読める場所。読み手は子ども |

**Phase 0 は作ってある。** 動くものは次の2つ。

| | | |
| --- | --- | --- |
| [`../biz/`](../biz/) | **ハタラク文庫（仮）** | Markdownで書いた記事が、そのまま記事ページになる。**書く画面つき** |
| [`../ehon/`](../ehon/) | **えほんの棚（仮）** | ページをめくって読む。ふりがな・読み上げ・オフライン。**つくる画面つき** |

書く／つくる画面は、**まだどこにも送らない**。書いたものは端末の中だけに残り、
ファイルとして持ち出す。Phase 1 でつないだら、そこが「保存」に変わる。

2つは**同じ土台の上に載せる**。この文書は、その共通部分とお金の話。
中身の違いは各ファイルに書いてある。

## 0. 前提

**軌道に乗るまで、我々の支払いはゼロにする。ユーザーが払うのは可。**

この2つは両立する。**払う人を分ければいい。**

| | 誰が払うか | 我々の負担 |
| --- | --- | --- |
| サーバー・配信 | 無料枠に収める | **ゼロ** |
| 決済手数料 | 売上から自動で引かれる | **ゼロ**（持ち出しがない） |
| 作者への支払い | 買った人のお金がそのまま作者へ | **ゼロ**（我々を経由しない） |

肝は「安く済ませる」ではなく、**固定費を1円も発生させない形を選ぶこと**。
月額のかかるものを1つ入れた時点で、売上ゼロの月に赤字が出る。以下はその条件で選んである。

## 1. 我々の費用をゼロに保つ構成

| 役割 | 使うもの | 我々の費用 | 条件 |
| --- | --- | --- | --- |
| 配信（HTML・CSS・JS・画像） | **Cloudflare Pages 無料** | **0円** | 帯域・リクエスト無制限。**商用利用可**。カード登録不要 |
| DB・ログイン・サーバー処理 | **Supabase 無料** | **0円** | 商用利用可。カード登録不要 |
| 決済 | **Stripe Connect（Standard）** | **0円** | 月額なし。**手数料はStripeが作者に直接請求する** |
| ドメイン | **取らない**（2026-08-16 決定） | **0円** | 独自ドメインは作らない |

数字は2026年8月時点。**各社よく変わるので、使う前に必ず最新を確認する。**

### 置き場所をなぜ Cloudflare Pages にするか（Netlify・Vercelとの比較）

| | 帯域 | デプロイ | 上限を超えたら | 商用利用 | カード |
| --- | --- | --- | --- | --- | --- |
| **Cloudflare Pages** | **無制限** | 500回/月（別勘定） | 起きない | **可** | 不要 |
| Netlify（いま作るアカウント） | **実質15GB/月** | **帯域と同じ財布** | **サイトが停止** | 可 | 不要 |
| Vercel Hobby | — | — | — | **不可（規約違反）** | 不要 |

**Vercel Hobby は個人の非商用向け**なので、有料販売をするなら最初から選べない。

**Netlify は使えるが、条件が悪い。** 2025年9月から新しいアカウントは
**クレジット制**（月300クレジット）になっていて、帯域とデプロイが同じ財布から出る。

| | 消費 | 300クレジットで |
| --- | --- | --- |
| 帯域 | 20クレジット/GB | **15GB/月** |
| デプロイ | 15クレジット/回 | **20回/月** |

つまり**デプロイを20回すると、その月の帯域はゼロ**。
記事や絵本を足すたびにデプロイする作りとは噛み合わない。
（2025年9月3日以前からあるアカウントは旧方式で、帯域100GB＋ビルド300分。
いま新規に作るなら関係ない）

上限に達したときの挙動も見ておく。

| | 超えたとき |
| --- | --- |
| **Netlify 無料** | **その月の残りサイトが停止する。勝手に課金はされない** |
| **Cloudflare Pages 無料** | 帯域・リクエストが無制限なので、そもそも起きない |

**勝手に課金されない点は Netlify も安心できる。** ただし止まると真っ暗になるので、
公開する場所には向かない。**本番は Cloudflare Pages。**

### いちばん大事な設計ルール

> **配信は Cloudflare Pages。Supabase を経由して本文や画像を配らない。**

理由は無料枠の形が正反対だから。

| | 帯域 | 尽きるまで |
| --- | --- | --- |
| Cloudflare Pages 無料 | **無制限** | 尽きない |
| Supabase 無料 | **5GB/月** | 絵本なら月1,600冊、記事なら月1.7万PV |

**Supabaseから配ると、開いた初月に止まる。Cloudflareから配れば止まらない。**
Supabaseは「書き込み」と「いいね・コメント」だけに使う。JSONのやりとりなら
1回2KB程度なので、5GBで月250万回。当分足りる。

代わりに Cloudflare Pages 側の上限が効く。

| | 上限 | 意味 |
| --- | --- | --- |
| ファイル数 | 20,000／プロジェクト | **絵本なら約1,000冊**（20ページ×20枚）。記事なら実質無制限 |
| ビルド回数 | 500回／月 | **1日16回の公開まで**。審査してから公開する運用と噛み合う |
| 1ファイル | 25MB | 絵本の画像には十分 |

ファイル数が本当に足りなくなったら Cloudflare R2（10GB無料・転送量無料）だが、
**有効化に支払い方法の登録を求められるという報告がある。そこは相談ライン。**

### GitHub Pages に有料販売を載せてはいけない

いま `todo2023.github.io` を配信している GitHub Pages には、**規約上の制限がある。**

> GitHub Pages は、オンラインビジネス・ECサイト、その他**主に商取引を目的とするサイト**を
> 無料でホスティングする用途には使えない。ただし**寄付ボタンやクラウドファンディングへのリンク**などは許容される。

読み替えるとこうなる。

| | GitHub Pages |
| --- | --- |
| 無料公開だけ | **OK** |
| 投げ銭・支援リンク | **OK**（寄付として許容の範囲） |
| 記事や絵本の**有料販売** | **NG。規約違反になる** |

**なので、売る予定があるなら最初から Cloudflare Pages に置く。**
既存のアプリ置き場（`../README.md` のもの）はそのままで問題ない。

### 決済は Stripe Connect の Standard を使う

「ユーザーが課金するのは可」を、**我々の固定費ゼロのまま**成立させる唯一の形。

| | プラットフォーム（我々）の費用 |
| --- | --- |
| **Standard** | **なし。Stripeが作者に直接請求する** |
| Express / Custom | **1アクティブアカウントあたり月 $2 ＋ 入金ごと 0.25%＋$0.25** |

Express/Custom は、**作者が100人いれば売上ゼロでも月$200かかる。** 選んではいけない。

Standard を選ぶと、ほかにも効く点がある。

- 作者が自分のStripeアカウントで受け取るので、**我々がお金を預からない**
  （預かると収納代行・資金決済法の話が出てくる。避けられる）
- 手数料（国内カードで3.6%前後）は売上から引かれる。**売れなければ1円も出ない**
- 我々の取り分は `application_fee` として上乗せできる。取らない選択もできる

代わりに引き受けることがある。

- **売主は作者になる。**特定商取引法の表記義務は作者側に出る（個人だと住所の公開が壁になる）
- 我々は取引デジタルプラットフォーム側として、苦情窓口などの努力義務を負う
- 我々が手数料を取るなら、作者に対して請求を出す立場になる（インボイス・消費税の話）

**まず「投げ銭・支援」から始めて、有料販売は後にするのが軽い。** 上の事務がほぼ要らない。

## 2. 共通の土台

どちらも「Zennの設計」を下敷きにする。5層に分けると、共通にできる層と分ける層が分かれる。

| 層 | 中身 | 2つで共通か |
| --- | --- | --- |
| ① 配信・インフラ | 上のとおり | **共通** |
| ② アカウント | ログイン、プロフィール、フォロー、通知 | **共通**（子ども版は保護者アカウント） |
| ③ データの骨格 | 作品、トピック、いいね、コメント、通報 | **共通**（列名まで同じにする） |
| ④ 執筆・表示 | 何をどう書き、どう読ませるか | **別**。ここが2つの正体 |
| ⑤ 運用（審査） | 何を出してよいか、いつ誰が見るか | **別**。マーケは事後、子ども向けは事前 |

**①〜③を共通にすれば、2つ目を作るコストは半分以下になる。**
逆に④⑤を共通にしようとすると、両方とも中途半端になる。

## 3. 段階（全部ゼロ円）

| | やること | 我々の費用 |
| --- | --- | --- |
| **Phase 0 ✔できた** | 中身をリポジトリに置いて配信。作るのは身内だけ。投稿は受け付けない | **0円** |
| **Phase 1** | ログイン・投稿・反応を Supabase 無料枠で足す。招待制<br>（**書く／つくる画面は先に作ってある。送り先だけがない**） | **0円** |
| **Phase 2** | 一般公開、検索、通知 | **0円**（後述の上限まで） |
| **Phase 3** | **投げ銭 → 有料販売**。Stripe Connect Standard | **0円**（手数料は売上から） |

前の版では Phase 2 から有料としていたが、**配信を Cloudflare Pages に寄せれば、
Phase 3 まで固定費ゼロで行ける。** 有料になるのは次の3つに当たったときだけ。

| 壁 | いつ来るか | そのときの選択肢 |
| --- | --- | --- |
| Cloudflare Pages のファイル数 20,000 | 絵本 約1,000冊 | R2（要カード登録）／プロジェクトを分ける |
| Supabase の DB 500MB・ストレージ1GB | 記事 数万本 | Supabase Pro $25/月 |
| ビルド 500回/月 | 1日16回を超える公開 | 有料プラン／公開をまとめる |

**どれも「軌道に乗ってから」しか来ない。** そのときは売上がある。

### 決まったこと：独自ドメインは作らない（2026-08-16）

URLは `todo2023.github.io/my-ai-agent/...` のままにする。費用ゼロで確定。

ただし、これで**1つ先送りできない問題**が出てくる。

> **GitHub Pages は規約でECに使えない。**（上の節）
> つまり **Phase 3（有料販売）に進むなら、そのとき置き場所を移すことになる。**
> 移せばURLが変わり、それまでの検索の積み上げを失う。

なので、検索に出す前に**どちらかに決めておく**必要がある。どちらも0円。

| | URL | 有料販売に進めるか |
| --- | --- | --- |
| **GitHub Pages のまま** | `todo2023.github.io/my-ai-agent/biz/` | **進めない**（進むならURLを捨てる） |
| **Cloudflare Pages に移す** | `〇〇.pages.dev` | **進める**。移さずに済む |

**投げ銭までなら GitHub Pages でよい**（寄付は規約上OK）。
販売までやる見込みがあるなら、検索に出す前に Cloudflare Pages に移しておくほうが安い。
移すのはいまなら数分で、失うものもない。

## 4. それでも相談が要ること

`../CLAUDE.md` の決まりに沿って先に挙げる。**どれもまだ着手していない。**

1. ~~独自ドメイン~~ … **作らないと決めた（2026-08-16）。この項目は終わり**
2. **Cloudflare R2**（絵本が1,000冊を超えたら）… 無料枠の範囲だが、
   **有効化に支払い方法の登録が要る可能性がある。カード登録は相談事項**
3. **Supabaseのプロジェクト数** … 無料は2つまで。2サービスで使い切る
4. **Claude API**（審査の一次スクリーニングなど）… 使うなら `../hp/match/` と同じ歯止め

   **Phase 0/1 では使わない前提**
5. **有料販売に進むタイミング** … 投げ銭までは事務がほぼ不要。
   販売に進むと特商法・インボイスが乗る。**機能より事務が重い**

## 5. 共通のデータ設計

2つで**列名まで同じにする**部分。`../hp/match/` と同じく、読み取りは RLS で止める。

| テーブル | 中身 |
| --- | --- |
| `users` | Supabase Auth（メールのリンク方式。パスワードを持たない） |
| `profiles` | 表示名・自己紹介・リンク |
| `works` | 作品（記事／絵本）。`slug` `title` `topics[]` `status` `published_at` |
| `topics` | トピック。マスタを持って表記ゆれを防ぐ |
| `likes` `comments` `follows` | 反応 |
| `notifications` | 通知 |
| `reports` | 通報。**あとから足すと過去分に対応できない。最初から持つ** |
| `stripe_accounts` | 作者のStripeアカウントID。**Phase 3で使う。器だけ先に作る** |
| `products` `purchases` | 販売・購入 … **後日** |

`works.status` は `draft` / `review`（審査待ち）/ `published` / `rejected` の4つ。
マーケ版は `review` を素通ししてよいが、**子ども版は人が通さないと公開しない**。
状態を共通にしておけば、運用の厳しさだけ切り替えられる。

**下書き（`draft`）が anonキーで読めてしまう事故が一番怖い。**
公開前チェックの必須項目にする。
