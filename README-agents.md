# AIエージェント構築カリキュラム（10%ルール活用）

## 0. この取り組みについて

### 目的

AX案件に対応できる状態を、案件が本格化する前に作ることが目的です。

ただし「案件のために勉強する」だと続きません。自分が使いたいものを作る、その過程で必要な技術が身につく、という順序で設計しています。題材は各自が決めてください。

### 何を身につけるか

AIエージェントは「作れること」自体はもう差別化になりません。チュートリアルをなぞれば動くものはできます。

差がつくのは次の3点です。このカリキュラムはここに重心を置いています。

- どこをLLMの判断に任せ、どこを決定的な処理で固めるかを設計できる
- なぜ失敗したかを切り分けられる（検索か、プロンプトか、モデルか、そもそもデータに無いのか）
- 精度・コスト・レイテンシを数値で語れる

顧客先で問われるのは「作れますか」ではなく「どれくらいの精度で、いくらかかりますか」です。

### 進め方の原則

- 期限なし・各自のペース。繁忙期は止めて構いません
- ただし進捗は公開の場に書く。詰まったまま黙って消えるのが唯一の失敗パターンです
- 理論は詰まってから取りに行く。先に本を読み切ろうとすると10%が消えます

## 1. テーマの決め方

### 例として挙げるテーマ

以下は例です。この中から選んでも、まったく別のものでも構いません。

| テーマ | エージェントとして学べる要素 | 評価のしやすさ |
| --- | --- | --- |
| 旅程プランナー | 制約充足、矛盾時の聞き返し、再計画 | △（主観的） |
| ゲームAI（人狼・麻雀・交渉） | マルチエージェント、役割分担、階層的委任 | ◎（勝率） |
| 自律コーディングエージェント | ReAct、セルフリフレクション、テスト駆動ループ | ◎（テスト通過率） |
| 献立・買い物エージェント | 複数制約の同時充足、在庫状態の管理 | △ |
| ディープリサーチ | 検索計画の自己生成、情報の信頼性判断、コスト管理 | ○ |
| 個人秘書（常駐型） | 長期実行、割り込み判断、「いつ黙るか」の設計 | △ |

### テーマ選びの条件

自由に決めて良いですが、次の3つは満たしてください。満たさないと途中で学びが止まります。

- 自分が実際に使いたい（他人のために作るものは改善が続きません）
- 複数のツール／外部データを使う（単発のAPI呼び出しで完結するものはエージェントになりません）
- 失敗しうる（毎回正解が出るものは、評価もエラー分析も学べません）

「良い出力とは何か」を定義しにくいテーマは難易度が上がります。迷ったら、勝敗やテスト結果のような客観指標が最初から存在するテーマを推奨します。

### 使う技術（ここは揃えます）

題材は自由ですが、基盤は統一します。バラバラだと相談が成立せず、知見が合流しないためです。

- エージェントフレームワーク：LangGraph（またはGoogle ADK）
- オブザーバビリティ：Langfuse（またはLangSmith）
- 外部ツール接続：MCP
- モデル：任意。ただしコスト比較のため最低2種類は試すこと
- 言語：Python（理由と準備は次項）

## 1.5 準備：Python

### なぜPythonか

TypeScriptでも同じものは作れます。それでもこのカリキュラムではPythonを指定します。学習が目的なので、詰まったときに情報が見つかる方を選ぶという判断です。

- LangGraph、LangChain、Langfuse とも、実装例・ドキュメント・コミュニティの厚みがPython側に偏っている
- Google ADK や Vertex AI のサンプルも基本Python
- 新しい手法の検証コードや論文実装は、まずPythonで出てくる
- 評価とエラー分析でデータをいじる場面が必ず来る。pandasが使えると作業速度が変わる

なお当社では製品でも一部Pythonを使っており、適材適所で使い分ける方針です。このカリキュラムで得た実装がそのまま製品に入る場面もあれば、TypeScript側で書き直す場面もあります。どちらの言語も選択肢として持っておく、という位置づけで捉えてください。

### 必要なレベル

深い習熟は不要です。TypeScript経験があれば1〜2週間で足ります。

- 基本文法と型ヒント
- async / await
- uv での環境・パッケージ管理
- pandas の基礎（読み込み、フィルタ、集計）
- Jupyter または Colab での試行錯誤

環境管理は uv を使ってください。Python経験者がつまずく箇所の大半（venv、pip、バージョン競合）がここでほぼ解消します。

### Python未経験の場合

最初の1〜2週をここに充てて構いません。ただし文法を網羅しようとしないこと。上のチェックリストが埋まったらゲート1に進み、足りない部分は必要になった時点で埋めてください。

## 2. 5つのゲート

期限は設けませんが、通過順序は固定です。各ゲートには「これができたら通過」という明確な条件があります。

### ゲート1：動くエージェント

まず何でもいいので動かします。品質は問いません。

**やること**

- テーマを決め、最小構成で動くものを作る
- MCPまたはツール呼び出しで、外部の何かを最低1つ叩く

**通過条件**

- 人が指示を出すと、ツールを使って何かを返す
- 誰かに1回デモした

**このとき学ぶ理論**

- ツール利用（Function Calling / MCP）の仕組み
- ReActパターン：思考 → 行動 → 観察のループ
- コンテキストウィンドウとトークンの基礎

**つまずきやすい点**

- 最初から完璧な設計をしようとして進まない。汚くていいので動かす
- ツールが多すぎてLLMが選べない。まず2〜3個に絞る

### ゲート2：壊す

ここが一番重要なゲートです。多くの人がゲート1で満足して止まりますが、実力がつくのはここからです。

**やること**

- 自分のエージェントが失敗する入力を30個集める
- それぞれについて、失敗の原因を分類する
  - 入力データの問題（そもそも情報が無い）
  - 検索・取得の問題（必要な情報を取ってこられなかった）
  - プロンプトの問題（指示が曖昧、形式が崩れる）
  - モデルの能力の問題
  - ツール設計の問題（LLMがツールを選び間違える）

**通過条件**

- 失敗ケース30件の一覧と、原因分類の表がある
- 「どの分類が一番多いか」を説明できる

**このとき学ぶ理論**

- エラー分析の手法
- 構造化出力とスキーマ検証
- プロンプト設計の型（few-shot、役割指定、出力形式の固定）

**なぜこれをやるか**

顧客先で「精度が出ない」と言われたとき、原因を切り分けられるかどうかが実力差です。ここを飛ばすと、「プロンプトをいじってみる」以外の手が出せなくなります。

### ゲート3：構造化する

ゲート2で見つけた問題を、設計で解きます。

**やること**

- LangGraphで多段のワークフローに分解する
- LLMに任せる部分と、決定的なコードで固める部分を分ける
- 状態管理を実装する（途中で失敗したらどこから再開するか）
- 不可逆な操作の前に承認ゲートを入れる（送信、削除、購入など）

**通過条件**

- ワークフロー図が描ける（何がLLM判断で、何が固定処理か色分けされている）
- 途中で失敗しても、最初からやり直しにならない
- 「なぜここをLLMに任せなかったか」を説明できる

**このとき学ぶ理論**

- 状態管理とチェックポイント
- Human-in-the-Loop（HITL）の設計
- 階層的委任、マルチエージェントの分割方針
- エージェントに実行権限を渡す際のセキュリティ設計

**補足**

「全部LLMにやらせる」と精度もコストも悪化します。判断が必要なところだけLLM、あとは普通のコード、という切り分けができるかどうかが設計力です。実務ではここが提案の説得力に直結します。

### ゲート4：測る

AX案件で最も差がつくのがこのゲートです。作れる会社は多いですが、精度を数値で語れる会社は多くありません。

**やること**

- Langfuse等を導入し、全実行をトレースする
- 以下を計測する
  - 1リクエストあたりのトークン数とコスト
  - レイテンシ（どのステップが遅いか）
  - 成功率（自分で定義した「成功」の基準で）
- 評価データセットを20件以上作る（入力と期待される結果のペア）
- モデルを変えて比較する（安いモデルで十分な処理はどれか）

**通過条件**

- 「このエージェントの成功率は◯%、1回あたり◯円、平均◯秒」と即答できる
- 改善前後の数字を比較できる
- コストを下げる打ち手を1つ以上実施した

**このとき学ぶ理論**

- 評価指標の設計（何をもって成功とするか）
- LLM-as-a-Judge の使いどころと限界
- トレーシングとオブザーバビリティ
- モデル選定とコスト最適化

**つまずきやすい点**

「成功」の定義が難しくて手が止まる。まず粗い定義で始めること。定義を洗練させるのも学習の一部です

### ゲート5：説明する

技術ではなく、伝える力のゲートです。

**やること**

- 社内デモ会で発表する（15分）
- 以下を顧客に説明する想定で話す
  - 何ができるか
  - 何ができないか
  - 精度はどれくらいか、どう測ったか
  - いくらかかるか（トークンコスト＋インフラ）
  - どこに人間の確認が必要か
- 技術ブログ記事を1本書く（社外公開想定、失敗談歓迎）

**通過条件**

- デモ会で発表した
- 記事のドラフトができた

**なぜ記事まで書くか**

会社の技術PR施策と直結します。学習した内容が対外的な資産にもなるので、時間の投資が二重に回収できます。うまくいった話より、失敗して直した話のほうが価値があります。

## 3. お互いに相談する仕組み

### 固定ペアにしない理由

繁忙期が人によって違うため、固定ペアだと片方が忙しいときに両方止まります。固定の一巡ローテーション（A→B→C→A）も、全員が同じ進度である前提が必要で、期限なしの運用とは噛み合いません。

### 採用する方式：ゲート通過レビュー制

各ゲートを通過するとき、レビュアーを1人指名します。

- レビュアーはそのゲートを既に通過した人から選ぶ（先行者が自然と教える側になる）
- 誰も通過していない場合は、誰でも良い
- レビューは30分の口頭説明でOK。資料は不要
- レビュアーは「通過を認める／もう少し」を判断する

**この方式の利点**

- 進度が違っても成立する
- 先に進んだ人が教えることで、その人自身の理解も定着する
- 全員が「教える側」と「教わる側」の両方を経験する
- 忙しい人がボトルネックにならない（レビュアーは複数の候補から選べる）

**レビュアー側の心構え**

正解を教える必要はありません。「なぜそうしたのか」を質問するだけで十分です。説明できないところが、本人の弱いところです。

### 常時オープンな場

- 専用Slackチャンネルを作ります
- 詰まったら書く、解決したら書く、面白いものを見つけたら書く
- 「今日は進まなかった」も書いてOK。沈黙が続くのだけが問題です
- 週1回、自分の進捗を1行書く（ボットでリマインドします）

### 月1回のデモ会（30分）

- 動いていなくても参加・報告する
- 全員が今どのゲートにいるかを共有する
- 止まっている人を責めない。繁忙期は誰にでもあります。ただし止まっていることが見えている状態は維持する

## 5. よくある質問

**Q. 週にどれくらい時間を使えばいいですか**

10%＝週4時間が目安です。ただしカレンダーにブロックを入れてください。「空いた時間に」では必ず消えます。

**Q. 途中で止まってもいいですか**

構いません。ただし止まるときはSlackに一言書いてください。再開時のハードルが下がります。

**Q. テーマを途中で変えてもいいですか**

ゲート2までなら自由に変えてください。ゲート3以降での変更は、それまでの学びが流れるのでおすすめしません。

**Q. 全員が最後まで到達する必要がありますか**

ありません。全員が同じ水準になることは期待していません。深く到達した人が案件のリードになり、他のメンバーはその人から学べる、という状態が作れれば成功です。

**Q. Pythonを書いたことがありません**

問題ありません。1.5節のチェックリストの範囲だけ押さえれば十分です。TypeScript経験があれば1〜2週間で足ります。この期間もカリキュラムの一部として10%枠を使ってください。

**Q. TypeScriptで作ってはいけませんか**

禁止はしませんが推奨しません。詰まったときの情報量が違い、相談相手も減ります。学習効率を優先してください。製品への実装時に言語を選び直すのは別の話です。
