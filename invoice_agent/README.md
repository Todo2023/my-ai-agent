# 請求書エージェント

Excelの請求データから、**自然文の指示で請求書PDFを作る**エージェント。

```
$ uv run graph_agent.py "A社の請求書を作って"
A社の請求書を作成しました（invoice_A社.pdf）。

$ uv run graph_agent.py "A社の請求書を、割引10%つけて作って"
割引10% には対応していません。この部分を反映せずに作成してよいですか？ [はい/いいえ]:
```

**この2つ目が、このエージェントの全部**。対応していない要求を黙って無視して
作ってしまわないよう、実行の手前で必ず人に確認を取る。

## お金の話（先に）

| 使うもの | 費用 | カード登録 |
| --- | --- | --- |
| Gemini API（Google AI Studio のキー） | 0円 | 不要 |
| Python・LangGraph・fpdf2 ほか | 0円 | 不要 |
| 外部サービス（DB・ホスティング等） | **使わない**。端末の中だけで完結する | — |

**キーに課金アカウントを紐付けないこと。** 紐付けていなければ、無料枠を超えたときに
課金されるのではなく **429（レート制限）で止まる**。決まりは [`../CLAUDE.md`](../CLAUDE.md)。

1件あたりのLLM呼び出しは**1回だけ**、平均**約220トークン**（実測。下の「ゲート4」参照）。
円換算の単価は裏取りできていないので書かない。

## まず動かしてみる（APIキー不要）

```bash
python3 demo.py          # 全ケース
python3 demo.py --list   # ケースの一覧だけ
```

LLMを呼ばない。呼ぶ代わりに「LLMがこう読み取ったことにする」ぶんを差し替えて、
**そのあとの処理は本物のまま**動かす。9ケースが順に流れる。

これで意味があるのは、このエージェントが **LLMに「情報を抜き出す」ことしかさせていない**
から。実行してよいかの判断も、画面に出す文章も、全部コード側にある。
だからLLMを止めても、安全／危険の分かれ目はそのまま再現できる。

`fpdf2` と `openpyxl` だけ入っていれば動く。

```bash
pip install fpdf2 openpyxl
python3 make_sample_data.py   # sample_data.xlsx が無いとき
python3 demo.py
```

## APIキーを使って動かす

1. [Google AI Studio](https://aistudio.google.com/apikey) で無料のキーを作る
   （**課金アカウントは紐付けない**）
2. `.env` に書く

   ```
   GEMINI_API_KEY=...
   ```
3. 動かす

   ```bash
   uv sync
   uv run make_sample_data.py       # サンプルの請求データを作る
   uv run graph_agent.py "A社の請求書を作って"
   ```

キーが無いまま `graph_agent.py` を動かすと、何をすればよいかを書いたエラーが出る
（`import` しただけでは落ちない。`demo.py` を動かせるようにするため）。

## ゲート2で何が壊れたか

30通りの指示を流して分類した（全部 [`gate2_findings.md`](gate2_findings.md)）。
危なかったのはこの4つ。

| | 何が起きたか | なぜ |
| --- | --- | --- |
| #18 | 消費税に対応していないのに「**消費税込みで作成した**」と嘘の報告 | 実行結果の説明文までLLMに書かせていた |
| #15 | 割引の要求を黙って無視して、**確認なしにPDFを確定** | 実行してよいかの判断をLLMに委ねていた |
| #21 | 存在しないツール名を呼んで **`KeyError` でクラッシュ** | ツールの選択・実行までLLM任せだった |
| #9 | 「全部の顧客の請求書」に**手段が無かった** | ツールの機能不足 |

原因でいちばん多かったのは「ツール設計の問題」。ただし実務で怖いのは
**ハルシネーション（#18・#24）**。請求金額の話で嘘の完了報告が出るのは致命的。

## ゲート3でどう直したか

**LLMの仕事を「自然文から情報を抜き出す」だけに絞った。**

```
指示 → parse(LLM) → resolve_customer(コード) ─┬→ generate(コード)
                                              ├→ ask_confirm(人に確認)
                                              ├→ ask_customer(人に聞く)
                                              └→ out_of_scope(コード)
```

- **顧客名の解決**（`a社`→`A社`、`A社様`→`A社`）は `difflib` の決定的な処理。
  LLMの気分で毎回変わるのを防ぐ
- **実行してよいかの判断**はコードの条件分岐。ここをLLMに委ねると #15 が再発する
- **画面に出す文章はコードが組み立てる。** LLMに「何をしたか」を語らせない。
  これで #18 のような嘘の報告が**構造的に**起きなくなる

図と、なぜそう分けたかは [`gate3_notes.md`](gate3_notes.md)。
状態は `SqliteSaver` に保存していて、質問を出して終了した別プロセスから
続きを再開できることも確認済み。

## ゲート4：測ったら、大きいモデルのほうが悪かった

22件の評価データセット（`eval_dataset.json`）で2モデルを比較した。

| モデル | 成功率 | LLM呼び出し平均 | 平均トークン/件 |
| --- | --- | --- | --- |
| **gemma-4-26b-a4b-it**（小型・MoE） | **90.9%**（20/22） | **1.14秒** | 219.6 |
| gemma-4-31b-it（大型） | 68.2%（15/22） | 1.48秒 | 223.2 |

大きいほうは **6/22件でJSON形式を守れずクラッシュ**した（小型はゼロ件）。
速度も約30%遅い。「大きい・新しいモデルほど良い」は成り立たなかった。

この結果を受けて、標準モデルは `gemma-4-26b-a4b-it` に確定してある
（`graph_agent.py` の `MODEL`）。詳細は [`gate4_findings.md`](gate4_findings.md)。

```bash
uv run eval_run.py gemma-4-26b-a4b-it   # 測り直す（APIキーが要る）
```

## できないこと

対応していない要求は、**確認を挟むだけで実行しない**。

- 割引・消費税・支払期限の指定・品目の追加変更・出力形式の変更（Excel等）・メール送信・削除
- 複数の顧客を1回で名指しする（「A社とB社」）→ 聞き返しに倒れる
- 会話の文脈を覚える（「さっきの続きで」）→ 毎回聞き返す
- カタカナ表記の顧客名（「エー社」→「A社」）→ 解決できず聞き返す

**まだ本番には出せない。** 理由は3つ。

1. 「全ての顧客データを消して」を、削除依頼ではなく**請求書の一括作成と誤認する**
   （両モデル共通。`out_of_scope` になるべきところが `generate` 側に行く）。
   削除・送信のような取り消せない操作への防御が、いまのガードでは足りない
2. 複数顧客の同時指定が未対応
3. 円換算のコストを裏取りできていない
