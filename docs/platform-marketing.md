# マーケ・ビジネス版コミュニティ（設計メモ）

Zennのように**Markdownで手軽に書けて、公開して、反応がもらえる**場所を、
マーケティング・ビジネス領域で作れるか、という検討。まだ何も作っていない。

インフラ・費用・段階は [`README.md`](README.md) に共通で書いてある。ここは中身の話。

## 1. 結論

| 問い | 答え |
| --- | --- |
| Markdownで書けて、記事・いいね・コメント・フォロー・トピックがある場所を作れるか | **作れる** |
| Zennと同じ設計でよいか | **8割はそのままでよい。2割は変えないと成立しない** |
| 無料で作れるか | **立ち上げ期（月1万PV・書き手10人規模）は作れる** |
| Zenn同等規模まで無料で行けるか | **行けない。途中で必ず有料になる** |

「お金の発生部分以外なら」という前提だと、答えは**ほぼYes**。
ただし注意が1つあって、**お金は「収益化機能」だけでなく「規模」からも発生する。**
Zennは月1,000万PV・会員10万人の規模で、これはサーバー代が月数万〜十数万円かかる世界。
設計をZennに合わせること自体は無料でできるが、**Zennと同じ規模になった瞬間に有料になる。**

なので方針は「**設計はZennに合わせる／規模は段階に分けて、無料枠で止まる線を先に決める**」。

## 2. Zennの設計を分解する

| 層 | Zennのやり方 | 真似るか |
| --- | --- | --- |
| ① 執筆 | Webエディタ ＋ GitHub連携（ローカルで書いてpushすると反映） | **変える**（後述） |
| ② 変換 | Markdown → HTML。コードブロック・数式・図・埋め込み | **ほぼそのまま**。埋め込みの種類だけ差し替え |
| ③ データ | 記事 / 本 / スクラップ / トピック / Publication（組織） | **そのまま**。呼び名だけ変える |
| ④ コミュニティ | いいね・コメント・フォロー・トレンド・通知 | **そのまま** |
| ⑤ 配信 | Google Cloud（Cloud Run に Next.js と Rails、Cloud Buildで自動デプロイ） | **変える**。同じ構成は重すぎる |

①〜④が「Zennと同じ設計で作れるか」への答えで、そこはYes。
⑤はZennの**規模**の解き方であって、立ち上げ期の解き方ではない。

## 3. そのまま真似てはいけない3点

技術者コミュニティとビジネス系コミュニティの違いから来る。ここが設計の本題。

### (1) GitHub連携は要らない。むしろ害になる

ZennがGitHub連携を持っているのは、**読者と書き手が全員エンジニアだから**。
マーケター・経営者・事業開発の人はGitHubを開かない。ここを真似ると書き手がゼロになる。

代わりに置くもの。

| | |
| --- | --- |
| Webエディタ（主） | 見たまま書けて、裏ではMarkdownで保存される形（リッチテキスト⇔Markdown変換） |
| Markdown直書き（副） | 書ける人向けにモードを切り替えられるようにする |
| 下書きの自動保存 | ブラウザ内に退避。`../hp/match/` のフォームと同じ考え方 |
| 取り込み | Google Docs / Notion から貼り付けても書式が壊れないようにする |

**「Markdownで手軽に」の"手軽"の意味が、書き手の職種で変わる。**
エンジニアには手軽でも、マーケターには記法そのものが壁になる。
Markdownは**保存形式として採用し、入力方法としては強制しない。**

### (2) 埋め込みの中身が違う

Zennで重要なのはコードブロック・Gist・数式。ビジネス系で重要なのは次。

- 図表・グラフ（施策の結果を出す）
- 表（比較・料金・KPI）
- スライド（発表資料の共有）
- 前後比較の画像（LP改善など）

**表とグラフをきれいに出せるかどうかが、このジャンルでの実質的な品質になる。**
コードのシンタックスハイライトに相当する投資先がここ。

### (3) スパムとステマの前提が違う

技術記事はスパムの旨味が薄い。**マーケ記事は集客そのものが目的になりうる**ので、
放っておくと「自社サービスへの誘導」「被リンク稼ぎ」「情報商材」で埋まる。
機能ではなく**運用の設計**で、最初から入れておかないと後で手遅れになる。

| 対策 | 中身 |
| --- | --- |
| 外部リンクの属性 | 本文中の外部リンクに `rel="ugc nofollow"` を付ける（被リンク目的の旨味を消す） |
| 初期は招待制 | 誰でも書ける前に、書き手を選ぶ期間を置く |
| 通報とミュート | `reports` を最初から持つ |
| PR表記 | 広告・案件記事のフラグを必須にする（**ステマ規制。2023年10月から景表法の対象**） |
| 分野の線引き | 投資・副業・美容健康は法規制（金商法・薬機法）に触れやすい。**扱わないと決めるのも設計** |

審査は**事後でよい**（Zennと同じ）。読み手が大人なので、公開してから消す運用が成り立つ。
ここが子ども版との決定的な違い（[`platform-kids.md`](platform-kids.md) 参照）。

## 4. データ設計（あとから有料化を足せる形にしておく）

共通部分は [`README.md`](README.md#5-共通のデータ設計)。この版で足すのは次。

| テーブル／列 | 中身 |
| --- | --- |
| `works.body_free` / `works.body_paid` | 本文を**最初から2つに分けて持つ** |
| `works.is_pr` | 広告・案件記事のフラグ |
| `publications` `publication_members` | 企業・チームのアカウント |
| `work_revisions` | 版。あとで「更新履歴」を出せる |

**`body_free` / `body_paid` に最初から分けておくのが肝。**
Zennは「本（チャプター単位）」で売るが、記事の途中から有料にする形を後で足すなら、
本文を1カラムに突っ込んだあとで分割するのは面倒になる。
いまは `body_paid` を常に空で運用し、表示側も見に行かない。**器だけ用意しておく。**

## 5. この用途では無料枠がどう当たるか

1記事あたり約300KB（文章＋画像2枚）とすると、Supabase無料の帯域5GB/月で**月1.7万PV**。

- **月1万PV・記事300本** → 無料枠に収まる
- **月10万PV・書き手100人** → 帯域とストレージが切れる。**有料へ**
- **Zenn同等（月1,000万PV）** → 無料枠の話ではない

延命の手は2つ。どちらもタダ。

1. **公開記事のHTMLを静的に吐いて GitHub Pages から配る**（帯域100GB/月）。
   DBは書き込みと反応だけに使う。読む人が多いほど効く
2. **画像は投稿時に縮小してWebPに変換**してから保存する。元画像は残さない

## 6. まだ決まっていないこと

- コンテンツの単位。Zennの「記事 / 本 / スクラップ」に対して何を置くか
  （案：記事／事例（施策と数字）／相談スレッド）
- トピックの初期セット（SEO・広告運用・BtoBマーケ・CRM・採用広報 …）
- 実名前提にするか、匿名を許すか。ビジネス系は**書き手の所属が信頼の中心**なので、
  技術系より実名寄りのほうが機能しやすい
- 既存の `../hp/`（会社サイト）の下に置くか、独立させるか

## 7. 使えるもの・注意

- **zenn-editor**（`zenn-cli` / `zenn-markdown-html`）はオープンソースとして公開されている。
  Markdown→HTML変換を自前で書かずに済む可能性がある。
  **使う前にライセンス条項を必ず確認すること**（商用利用・改変・表記義務の有無）
- 名前・ロゴ・配色・画面の作りを寄せすぎない。**設計を参考にするのは自由だが、見た目の模倣は別の問題**
