# ゲート5: 社内デモ用ノート（15分想定）

## 1. 何ができるか（3分）

「請求書を自動で作るエージェント」。自然文で指示すると、Excelの顧客データから請求書PDFを作る。

デモ手順（実演）:
```
uv run graph_agent.py "A社の請求書を作って"
```
→ 生成されたPDFを見せる

続けて、対応してない要求のケースも見せる（承認ゲートの動きが分かりやすい）:
```
uv run graph_agent.py "A社の請求書を、割引10%つけて作って"
```
→ 「割引には対応していません。作成してよいですか？」と聞き返す様子を見せる

## 2. 何ができないか（2分）

- 割引・消費税・支払期限の指定・品目の追加変更・出力形式（Excel等）の変更・メール送信・削除には対応していない（要求されても確認を挟むだけで、実行はしない）
- 複数の顧客を1回の指示で同時に名指しする（「A社とB社」）には対応していない（現状は聞き返しに倒れる、安全だが機能不足）
- 会話の文脈を覚えない（「さっきの続きで」は毎回聞き返す）

## 3. 精度はどれくらいか、どう測ったか（4分）

- 22件の評価データセット（入力と期待する挙動のペア）を用意し、自動実行して採点
- 標準モデル（gemma-4-26b-a4b-it）で**成功率90.9%**
- 比較のため別モデル（gemma-4-31b-it、より大きいモデル）でも同じテストを実施 → 成功率68.2%、レイテンシも30%遅い、JSON形式崩れで6/22件クラッシュ
- 「大きいモデルの方が良い」という思い込みが実測で覆った、という話をここで共有する（失敗談として面白いポイント）

## 4. いくらかかるか（2分）

- 1リクエストあたりのLLM呼び出しは1回のみ（設計上、判断はLLM、実行は決定的コードに分離しているため）
- 平均トークン数: 約220トークン/件
- 円換算コストは、開発環境の制約（ネットワーク制限・無料枠のみで課金アカウント未設定）で裏取りできていない。本番導入前に公式料金ページでの確認が必須、と正直に共有する

## 5. どこに人間の確認が必要か（3分）

- ツールが対応していない要求（割引・消費税など）を含む指示は、**実行前に必ず人に確認**を取る（承認ゲート）
- 顧客名が曖昧・不明な場合も、推測せず人に聞き返す
- 「全顧客データの削除」のような指示は、テストの結果、意図しない誤動作（削除依頼を請求書一括作成と誤認）が見つかっている。**削除・送信のような不可逆操作は、現状のガードでは不十分**なので、本番投入前に追加の対策が必要、という注意点として伝える

## 想定質疑（自分の中でも準備しておく）

- Q. なぜLangGraphを使ったのか？ → LLMに何でも任せると（ゲート1〜2の実験で）ハルシネーションや無確認実行が起きたため。判断の一部を決定的なコードに固定するため
- Q. 本番投入できるか？ → まだ。削除・送信系の防御が弱い、複数顧客同時指定が未対応、コストの裏取りができていない。ゲート2で見つけた通り、実データでの追加テストが必要
