# Pawtown（仮）— 4つの施設がある町

イメージ図の情報設計をそのまま形にした、飼い主コミュニティのMVP実装。
入口は**町のマップ**で、住人は「どの施設に行くか」で投稿の種類を選ぶ。

| 施設 | 吹き出し | 投稿の種類 | AIの関わり |
| --- | --- | --- | --- |
| **ひろば** | うちの子のことをみんなに知ってもらおう！ | うちの子紹介 | AIがペット目線の物語にする |
| **そうだん所** | 疑問はみんなで話し合おう！ | 質問・相談 | 書かない（本人の言葉のまま） |
| **まなび舎** | 楽しみながら学んじゃおう！ | 学び | 書かない |
| **マーケット** | 便利なグッズをシェアしよう！ | グッズ共有 | 書かない |

ひろばの物語を読んでいる流れの中で、似た境遇の子の物語がそっと差し込まれ、
気になったら**双方の承認を経て**飼い主同士がつながる。

> **経緯。** v1「AIマッチング主軸」→ v2「AI物語主軸」→ 現在「イメージ図に全面的に寄せた
> 4カテゴリの投稿型コミュニティ」。AI物語は**ひろばに投稿するときの補助機能**という位置づけ。
> 写真投稿とコメントは今回のスコープ外（下の「未実装」を参照）。

## 5分で動きを見る（Supabase・APIキー不要）

```bash
pip install -r requirements.txt
export DEMO_MODE=1

python cli.py map                                       # 町の4施設と投稿数
python cli.py members                                   # ダミー会員5名

# ひろば（AIが物語にする）
python cli.py ask mocha@example.com                     # 今日の質問（方式B）
python cli.py post mocha@example.com --text "スリッパを片方だけ隠されていた"

# ほかの施設（本人の言葉のまま）
python cli.py post tama@example.com --category question --text "みんなは暑さ対策どうしてる？"
python cli.py feed mocha@example.com --category question

python cli.py feed mocha@example.com                    # 町ぜんぶ＋レコメンド
python cli.py connect mocha@example.com sora@example.com --send
python cli.py respond <ID> a yes                        # 片方が承認 → まだ紹介しない
python cli.py respond <ID> b yes                        # 両方揃った → 紹介メール
python cli.py stats
```

`DEMO_MODE=1` の間、メールは送信されず、内容が表示されるだけ。
コマンドをまたいで続きを試せるよう、状態は `.demo_state.json` に保存される
（消せば初期状態に戻る。保存先は `PAWTOWN_DEMO_STATE` で変えられる）。

## 1. 町の構成（`town.py`）

投稿カテゴリ＝町の施設。`town.CATEGORIES` の1か所に、施設名・吹き出し・例文・
AIが本文を書くかどうかをまとめてある。施設を増やすときはここに1行足す。

**AIがペット目線で本文を書くのは「ひろば」だけ。** 質問・学び・グッズは
飼い主の言葉をそのまま保存する（`stories.compose`）。相談や質問をAIに書き直させると、
事実でないことが混ざって相談として成立しなくなるため。これはテストで固定してある。

## 2. ひろばの物語生成

投稿のきっかけに応じて3方式を使い分ける。**分岐はプロンプトのテンプレートだけ**で、
処理の流れは3方式とも共通（`stories.py`）。

| 方式 | いつ使うか | 入力 | コマンド |
| --- | --- | --- | --- |
| **A** 一言→AI脚色 | 通院・体調変化など事実を外せない場面 | 飼い主の短文 | `post <email> --type A --text "…"` |
| **B** 定期質問→自動生成 | 特に予定のない日。ハードルが最も低い | 質問への回答 | `ask <email>` → `post <email> --text "…"` |
| **C** 写真→解析→物語化 | 誕生日・季節イベント | 写真 | `post <email> --type C --image photo.jpg` |

- **今日の質問**は会員IDと日付から決定的に選ぶ（`stories.question_for`）。
  同じ日に何度開いても同じ質問、翌日には変わる。ランダムにすると再現できず検証が面倒になるため
- **方式Cは2段構え**。まず写真から「見えた事実」だけを取り出し、その文章を入力として物語にする。
  こうすると `posts.raw_input` に何が写っていたかが残り、変な物語が出たときに
  画像解析が悪いのか物語プロンプトが悪いのかを切り分けられる
- **既定の方式を記憶**する。初回に選んだ方式が `members.default_post_type` になり、
  以降はワンタップ投稿。2回目以降に `--type` で別の方式を選んでも既定は変えない
  （変えたいときだけ `--remember`）。判定は `stories.should_remember_default` の1か所

### 物語に必ず載せるガード

プロンプトに次を毎回入れている（`stories.STORY_PROMPT`）。

- 与えられた情報に無いできごとを作らない（特に通院や体調の話で事実を足さない）
- 健康や治療についての助言・診断めいた表現を書かない

LLMの応答が空だったときは保存せずテンプレートに落とす。運用を止めないため。

## 3. マッチング（副次機能）

独立した「マッチング画面」は作らない。**ひろばの**一覧の合間に、
**「〇〇ちゃんも実は同じ悩みを抱えていました」**という1文とその子の物語を差し込むだけ（`feed.py`）。

```
ルナちゃんの物語 …
モカちゃんの物語 …
こむぎちゃんの物語 …

  ── そらちゃんも、実は「しつけ」「留守番」のことで悩んでいました。
     そらちゃんの物語: …
     つながりたい: python cli.py connect mocha@example.com sora@example.com
```

- LLMの呼び出しは**一覧1回につき最大1回**。候補の絞り込みは `scoring.py` が決定的に行うので、
  会員が増えてもLLMに渡す量は増えない
- 差し込むのは**ひろばの物語だけ**。そうだん所やマーケットの一覧には差し込まない
- レコメンドで見せた物語は通常の新着としては出さない（同じ物語を二度出さない）
- 物語が少ないうちは、間隔を空けられる枚数までしか出さない（末尾に並ぶと広告に見えるため）
- 「つながりたい」を押しても、その時点では誰にもメールは飛ばない。
  マッチが `pending` で作られるだけ

### どこをLLMに任せ、どこを決定的に固めるか

| 処理 | 担当 | 理由 |
| --- | --- | --- |
| フォーム回答の正規化 | `models.py`（コード） | 実行のたびにタグが変わるとスコアが再現しない |
| 今日の質問の選択 | `stories.py`（コード） | 決定的なので、質問の当たり外れを後から検証できる |
| 物語の文章 | `stories.py`（LLM） | ここが商品価値そのもの |
| 候補の絞り込みとスコア | `scoring.py`（コード） | 犬種一致・悩みの重なりはコードで確実に書ける |
| レコメンドの一文 | `feed.py`（LLM） | 「さりげなさ」は文章側でしか出せない |
| 承認状態の遷移 | `flow.py`（コード） | 誤ると個人情報が漏れる。LLMには触らせない |
| メール文面の骨格 | `notify.py`（テンプレート） | LLMが書くのはマッチ理由の1〜2文だけ |

配点は `scoring.WEIGHTS` の1か所（悩みの重なり35・種別25・犬種20・エリア15・性格5）。
スコアは内訳付きで返るので、精度が悪いときに候補選びとプロンプトのどちらが原因かを切り分けられる。

## 4. 個人情報の扱い

- LLMに渡すプロフィールにメールアドレスを含めない（`Member.to_prompt_dict`）
- **双方が承認するまで、相手のメールアドレスは相手に渡さない**。承認依頼は必ず個別送信で、
  両者が同じ宛先欄に並ぶのは `status = matched` の紹介メールだけ
- 断られた事実は相手に通知しない
- 送信の直前に必ず人間の y/N を挟む（`notify.set_confirm_hook`）
- Supabase は RLS を有効化。公開ダッシュボードが読むのは件数だけの `dashboard_stats` ビュー。
  公開フィード用の `public_feed` ビューは物語とペット名だけを出し、飼い主は特定させない
  （既定では anon に grant していない）

これらはテストで固定してある（`test_pawtown.py` の「承認フロー」節）。

### 承認フローの状態遷移

```
pending ──(aが承認)──> approved_a ──(bが承認)──> matched → 紹介メール送信
   │    └─(bが承認)──> approved_b ──(aが承認)──> matched
   └──(どちらかが拒否)────────────────────────> rejected（相手には通知しない）
```

## 5. 本番セットアップ

### Supabase

無料枠でプロジェクトを作り、SQL Editor で `schema.sql` を実行する。
v1 のテーブルが既にある場合は、`schema.sql` 末尾のコメントにある `alter table` を先に流す。

### Googleフォーム

質問文は `apps_script/form_to_supabase.gs` の `QUESTIONS` と完全に一致させる。

| 質問文 | 形式 | 必須 |
| --- | --- | --- |
| ニックネーム | 記述式 | ✓ |
| メールアドレス | 記述式（メール形式） | ✓ |
| **ペットのお名前** | 記述式 | ✓ |
| ペットの種類 | ラジオ（犬 / 猫） | ✓ |
| 犬種・猫種 | 記述式 | |
| ペットの年齢 | 記述式 | |
| ペットの性格（複数選択可） | チェックボックス | |
| 悩んでいること（複数選択可） | チェックボックス | |
| お住まいのエリア（都道府県・市区町村） | 記述式 | |
| **物語の作り方（あとから変更できます）** | ラジオ（一言を書く / 毎日の質問に答える / 写真を送る） | |

冒頭にプライバシーポリシーへのリンクと、
「物語とペット情報がコミュニティ内で他の会員に表示されること」への同意を明記すること。

### Apps Script

`apps_script/form_to_supabase.gs` を回答スプレッドシートの Apps Script に貼り、
スクリプト プロパティに `SUPABASE_URL` / `SUPABASE_SERVICE_KEY` を登録して
`installTrigger()` を1回実行する。

### 実行

```bash
cp .env.example .env    # 値を埋める
python cli.py post <email> --text "…"
python cli.py feed <email>
```

メールを伴う操作は、最初のうち `PAWTOWN_EMAIL_DRY_RUN=1` を付けて文面だけ確認するのが安全。

### ダッシュボード

```bash
python dashboard.py                            # 端末に件数を表示
python dashboard.py --html public/index.html   # Netlifyに置く静的HTML
```

登録者数・物語数（累計/今週）・今週書いた人・マッチ成立・承認待ちを表示する。
**service_role キーはHTMLに埋めないこと**（`dashboard.py` は anon キーしか使わない）。

## 6. コスト

| 項目 | 費用 |
| --- | --- |
| Netlify / Supabase / Googleフォーム / Gmail | 無料枠 |
| LLM API | 唯一の変動費 |

物語は**投稿1本につき1回**（方式Cのみ画像解析と合わせて2回）、
レコメンドは**フィード1回につき最大1回**。会員数ではなく投稿数に比例する。

ハンドオフ資料ではClaude APIを指定しているが、本実装は既存の `travel_agent` /
`meeting_agent` と揃えて無料枠のあるGemini APIを使っている（ゼロコスト制約を優先）。
LLM呼び出しは `llm.py` に集約してあるので、Claude APIに戻す場合はこのファイルだけを差し替える。
プロンプトは資料の案（3-1 / 3-2）をそのまま使っている。

`GEMINI_API_KEY` が未設定でも動く。その場合、物語もレコメンドもテンプレートの組み立てになる
（文章は硬くなるが、フローの検証はできる）。

### 9 を実装していない理由

資料の 5. でも「課金ラインは投稿数上限／保存容量／物語クオリティ段階を今後検討」となっており、
何を制限するかが決まっていない。決まり次第、投稿数上限なら `store.create_post` の手前、
クオリティ段階なら `llm.py` のモデル選択に入れるのが素直（どちらも1か所で済む）。
先に会員ごとのプラン列を切ってしまうと、決定後に作り直しになるため入れていない。

### 10 の進め方（案）

1. `DEMO_MODE=1` で投稿からつながりまでを社内で1回通す
2. 実データ5〜10名を登録し、方式Bを2週間毎日回して**継続率**を見る（物語の質より先に、続くかどうか）
3. 物語を本人に見せて「この子らしいか」を5段階で聞く。低評価の回は `posts.raw_input` を見て、
   入力が薄いのか、プロンプトが弱いのかを切り分ける
4. レコメンド経由の `connect` 率と、承認率を記録する

## ファイル構成

```
town.py       町の構成（投稿カテゴリ・吹き出し・AIが書くかどうか）
llm.py        LLM呼び出しの一元化（ベンダーを差し替えるならここだけ）
stories.py    ひろばの物語生成（方式A/B/C）と今日の質問
feed.py       施設ごとの投稿一覧とレコメンド差し込み
models.py     フォーム回答の正規化と Member / Post / Match
scoring.py    決定的な事前スコアリング（配点・犬種グループ・都道府県マップ）
matcher.py    紹介理由の生成（副次機能）
store.py      Supabase REST（DEMO_MODE=1 ならローカルのダミー）
notify.py     メール文面と送信（確認フック・ドライラン）
flow.py       承認フローの状態遷移
cli.py        運用コマンド
dashboard.py  件数表示 / Netlify用HTMLの書き出し
fakes.py      デモ用ダミーデータ
schema.sql    Supabaseのテーブル・ビュー・RLS（v1からの移行SQL付き）
apps_script/  Googleフォーム → Supabase
```
